# AI-Assisted Development

## 1. Purpose

AI tools were used as development assistance for the HealTrip AI prototype, including implementation and review work. The developer retained responsibility for requirements, architecture, scope, accepting or correcting suggestions, and deciding what was ready to keep. AI output was treated as a proposal to inspect against the source code, API contract, assessment requirements, and observed behavior.

The repository preserves the decision log and manual prompt scenarios, but not a complete transcript of development conversations. This document describes the uses that are evidenced by those artifacts and the project work; it is not an exhaustive activity log.

## 2. Areas where AI was used

- **Architecture exploration:** assistance compared an LLM-led approach, deterministic workflow alternatives, and a hybrid design. The decision record captures the trade-offs and the decision to keep a bounded hybrid agent for the prototype.
- **Agent and tool design:** assistance was used to reason about registered tool calling, the backend allow-list, DTO validation, canonical values, and the separation between the LLM, domain services, Prisma, and PostgreSQL.
- **Prompt design and review:** the system prompt was reviewed against explicit English, Arabic, mixed-language, clarification, safety, no-result, and provider-grounding scenarios. `tes.md` records manually run examples and observed responses.
- **Backend implementation/review:** AI assistance was used while working through backend agent behavior and implementation details. The final code is the source of truth; this document does not claim that every backend line was generated by AI.
- **Frontend implementation:** AI assistance contributed to the React and TypeScript chat interface, including the API client, transcript state, retries, RTL/LTR rendering, and responsive components. The frontend client was checked against the existing NestJS request and response contract.
- **Documentation:** AI assistance is being used to draft these assessment-facing documents from the actual repository and `DECISION_LOG.md`.

## 3. Effective approaches

The approaches that produced useful reviewable results included:

- Providing explicit scope and constraints, such as keeping the frontend on the existing `/chat` API and not adding diagnosis, booking, or authentication features.
- Asking for architectural alternatives with concrete scenarios and trade-offs, then recording accepted decisions in `DECISION_LOG.md` rather than treating a generated recommendation as settled design.
- Supplying expected behavior and comparing it with actual model responses. The manual scenarios cover language changes across turns, mixed-language input, missing information, empty results, and unsupported provider facts.
- Checking proposed frontend behavior against actual DTO bounds and the real API shape instead of inventing request fields.
- Asking for edge cases around tool argument validation, unsupported specialties, safety blocking, and grounded results.

Representative prompt patterns, paraphrased rather than copied from private conversation history:

- “Compare the agent architecture options against the assessment scenarios and document the trade-offs.”
- “Review these expected and actual model responses; change only the system prompt where the behavior is prompt-related.”
- “Check whether a tool-calling design prevents unsupported provider facts and unsafe searches.”
- “Build the frontend against the current `POST /chat` contract and keep the work within the frontend scope.”

## 4. Manual review and corrections

AI proposals were reviewed against the application contract and manually observed behavior. The repository records several concrete corrections and constraints:

- Manual prompt runs in `tes.md` exposed responses that switched languages unexpectedly, mixed Arabic and English labels, changed a city name, or suggested unsupported contact or appointment follow-up. The current system prompt explicitly selects the output language from the latest user turn, maps only supported controlled values, preserves request qualifiers, and disallows unsupported availability, booking, contact, and provider claims.
- The decision log records that free-text provider summaries created opportunities for reinterpretation. `SearchDoctorsTool` and `SearchHospitalsTool` now return explicitly selected structured fields; summaries and internal IDs are not included in those results.
- Tool schemas use semantic specialty and city values rather than database IDs. The backend separately validates DTO input and checks specialty codes before querying.
- The current agent registry contains only `search_doctors` and `search_hospitals`. Clarification and final responses are natural-language messages, not invented executable tools or separate persisted action states.
- Safety behavior is described as a coarse backend pattern check. Neither prompt wording nor AI review is treated as a substitute for that server-side check.
- The frontend uses the existing API request/response fields. It does not call the LLM provider directly or fabricate provider cards, ratings, or availability.

The project records an OpenRouter adapter and a model target in `DECISION_LOG.md`. The current provider source and `backend/.env.example` do not agree on all model configuration names/values; this mismatch is identified in the README rather than hidden or “corrected” by documentation assumptions. The repository does not provide evidence for a historical provider switch caused by quota limits, so this document makes no such claim.

## 5. Engineering decisions that were not delegated to AI

The developer retained architectural ownership. Decisions recorded as accepted in `DECISION_LOG.md` include:

- Keeping the prototype to the hybrid agent design and a maximum of three tool-call iterations rather than introducing a full workflow/state-machine engine.
- Restricting execution to two backend-registered tools and validating their arguments independently of model output.
- Keeping the backend as the authority for database access, safety blocking, canonical specialty validation, and the facts returned to the model.
- Using a normalized `Specialty` model and explicit many-to-many join models; keeping city as a string and hospital services as a controlled enum for the MVP.
- Excluding subspecialty, raw provider summaries, booking, availability, and other unsupported healthcare-platform scope.
- Using an `LLMProvider` abstraction with the OpenRouter adapter rather than coupling `AgentService` directly to the SDK.

The full decision history and the status of earlier proposed alternatives remain in `DECISION_LOG.md`.

## 6. Validation

AI suggestions were not assumed to be correct. Validation evidence in this project includes:

- Inspecting the actual NestJS controller, DTOs, provider, tools, registry, services, Prisma schema, seed, frontend API client, and environment examples before documenting behavior.
- Running the manual system-prompt scenarios recorded in `tes.md`; those records include actual model outputs as well as expected behavior.
- The frontend implementation was checked with `npm run build` and `npm run lint`; both passed during the frontend work.
- Jest unit test files exist for the app controller, agent service, safety guard, chat service and DTO, and doctor and hospital services. The test commands are documented in the README. This documentation task did not rerun the backend tests, so it makes no claim about their current pass status.
- A Jest e2e scaffold is present, but its existing spec expects the Nest starter `GET /` response rather than exercising the current chat API. The README identifies this coverage gap.

Manual LLM scenarios are not a substitute for automated tests, and successful builds do not establish clinical safety or model correctness.

## 7. Example prompts and approaches

These short examples represent the style of requests used during development; they are not intended as a complete transcript:

- “Review the system prompt against these expected and actual English and Arabic chat results.”
- “Keep changes within the requested layer and do not alter the backend contract.”
- “Inspect the actual implementation before writing setup and architecture documentation.”
- “Check that returned provider facts are limited to the structured tool result.”

No API keys, credentials, or other secrets are included here, and local `.env` values were not inspected for this documentation task. The backend has an ignore rule for `.env`; a frontend `.env` file is present as an untracked file in this checkout, so verify local environment files before committing. Only the placeholder `.env.example` files were read as documentation sources.

## 8. Final principle

AI was used as an engineering assistant, not as the authority over the system design. Final implementation decisions were based on explicit assessment requirements, actual repository behavior, observed test scenarios, engineering trade-offs, and the developer-maintained decision log.
